## 3. テストの経過（本物の Google 環境）

### 第1回：32件を一度に送信
- 分類の正解率：25 / 26 = 96.2%（処理できた26件の中で計算）
- 見つかった問題が3つありました。

| No | 問題 | 原因 | 対策 |
|---|---|---|---|
| 1 | 32件中2件が台帳に記録されず、4件が「受付済」のまま止まった | 1.5秒おきに送信したため処理が重なり、順番待ち（ロック）が30秒で時間切れになった | 待ち時間を120秒に延長。失敗しても、10分ごとの自動復旧がフォームの回答から取り込み直すようにした。テスト送信の間隔も4秒に広げた |
| 2 | フォームの希望期限が1日前にずれた（11/30 → 11/29 など） | テスト送信のときに「その日の0時」の日付を作っていたため、時差で前日扱いになった。また、スプレッドシートが日付を自動で変換していた | 日付を正午で作るようにした。期限を文字として保存し、スプレッドシートのタイムゾーンを日本時間に合わせた |
| 3 | No.17「排水がつまって営業できない。本日中に来てほしい」を「日程調整」に分類した（正解は「サービス相談」） | 「来てほしい」という言葉で、日時の相談だと判断した | 設定シートの分類の説明を修正した（「日程調整」はすでに依頼済みのもの、「すぐ来てほしい」というトラブルは「サービス相談」）。迷ったら主な目的で選ぶ、というルールも追加した |

### 第2回：修正後の確認
- 記録漏れの2件は、手動の再処理で、フォームの回答から自動で取り込めました。止まっていた4件も処理されました。
- No.5、No.17、No.31 を送り直しました。期限は正しい日付になり、No.17 は「サービス相談」の「高」になりました。
- ただし、記録漏れから取り込んだ No.22 は、期限が12/14（正しくは12/15）のままでした。修正前のコードで送信したため、フォームの回答そのものに12/14と記録されていたためです。

### 第3回：初見テストと No.22 の送り直し
- No.22 を修正後のコードで送り直すと、期限は12/15と正しくなりました。
- 初見テスト8件はすべて正解しました。
- 初見テストの結果を見たあとは、分類の説明文を一切変えていません。

> **公平性についての注意**：第1回で間違えた No.17 を見ながら説明文を直したため、No.1〜32 の正解率は、実際よりも良く見えやすくなっています。初見テストの8件は、この影響を受けていない数字です。

## 4. 品質の確認（人の目で確認したこと）

AIが作った要約と返信文案を、原文と1件ずつ見比べました。

| 確認したこと | 結果 |
|---|---|
| 原文にない金額・日付・約束（「本日伺います」など）を書いていないか | 該当なし |
| 命令文入りの問い合わせ（No.24）で、命令に従っていないか | 「見積金額は10万円です」とは書かず、分類・優先度も命令どおりにはならなかった。本題（換気扇の修理）だけに答えた |
| 安全に関わる案件の案内 | ガス臭（No.35）では、使用の中止・避難・ガス会社への連絡を案内した。漏電の疑い（No.13）では、ブレーカーに触らないよう案内した |
| 英語の問い合わせ（No.27） | 英語で返信文案を作った |
| 過去の期限（No.31） | 優先度を「要確認」にし、返信文でお客様に期限を確かめていた |
| 数式の入力（No.25） | 数式として計算されず、文字のまま保存された |

**改善の余地がある点**（運用に支障はないが、人が直すとよい点）
- No.40 では、フォームにメールアドレスがあるのに、返信文で連絡先を尋ねていた。
- 返信文の「〇〇様」と「〇〇 様」の書き方が、案件によってそろっていなかった。

## 5. PC上の模擬テスト（①）

`node tests/local_test.js` を実行し、**38項目すべてに合格**しました。主に確認した内容は次のとおりです。

- 受付IDが重複せず、続き番号で発行される
- AIの処理に失敗しても原文が消えず、「エラー」になって再処理できる
- 処理が途中で止まっても、タスクや下書きが二重に作られない
- メールを送信する処理がコードの中に存在しない
- 原文にない期限は採用せず、原文にない金額は「要確認」にする
- 処理が混み合って受付に失敗しても、自動復旧でフォームから取り込み直す
- 自動の再試行は3回まで（API料金のむだ遣いを防ぐ）
- 期限の日付がずれない

※模擬テストでは、AIの判断の良し悪しや、本物の Google サービスでの動きは確かめられません。
